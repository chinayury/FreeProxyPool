# 01 - 项目介绍与架构

## 项目概述

FreeProxyPool 是一个轻量、可分布式扩容的**免费代理 IP 池系统**：自动采集公开免费代理 →
三层递进验证 → 标准化 API 分发，专为爬虫与自有测试提供低成本代理资源。

- **版本**：v0.1.0（版本号唯一来源：根目录 `VERSION` 文件）
- **许可**：Apache-2.0（见根目录 `LICENSE`）
- **技术栈**：Python 3.12 · FastAPI · Redis（Hash + ZSet + List）· aiohttp 异步校验
- **定位**：预期用于个人学习与自有爬虫测试

## 解决的核心问题

免费代理的公开来源普遍存在三个老问题，本项目针对每一点都做了闭环处理：

| 老问题 | 处理方式 |
|--------|----------|
| 采到的代理一半是死的，浪费调用方带宽 | 三层递进验证（TCP → 代理功能 → 多轮复检）+ 客户端失效回报接口 |
| 坏源一直拖慢每一轮采集 | 单源熔断（连续失败计数）+ "解析出 0 条即判失败" |
| 调用方发现代理失效只能等下一轮复检 | `POST /report/` 立即淘汰并拉黑 |

## 核心设计原则

1. **进程职责严格分离**：采集、验证、网关、调度四个进程互不重复触发，可独立扩缩容。
2. **单一实现、单一鉴权**：全项目只有一套 FastAPI 网关实现，不存在 Flask/FastAPI 双实现导致的行为分裂。
3. **版本单一来源**：版本号只来自根目录 `VERSION` 文件，避免代码、镜像标签、文档各写各的导致漂移。
4. **fail-closed 安全语义**：Redis 故障时鉴权不放开、限流不放开，行为是"拒绝服务"而非"放开大门"。
5. **文档与代码一致**：文档中的路径、命令、模块名均可在真实目录中对应。

## 系统架构

```
                    ┌──────────┐
   客户端 ─────────▶│  Nginx   │  统一入口 / 限流 / 静态资源反代
                    └────┬─────┘
                         │  (可 --scale gateway=N)
                    ┌────▼─────┐        ┌──────────────┐
                    │  gateway │───────▶│ Redis（权威） │◀──── collector
                    └────┬─────┘        │ Hash + ZSet  │◀──── validator
                         │              │ List(队列)   │◀──── scheduler
                    ┌────▼─────┐        └──────┬───────┘
                    │   MySQL  │◀──────────────┘（可选冷存储归档）
                    │  归档审计 │
                    └──────────┘
```

### 四个进程职责

| 进程 | 职责 | 可否多副本 |
|------|------|-----------|
| `collector` | 扫描采集源 → 过滤去重 → 推入待验队列 | 可 |
| `validator` | 消费队列 → 三层验证 → 写入有效池 | 可 |
| `gateway` | API 分发 + 管理后台 + 指标 | 可（推荐 2~4） |
| `scheduler` | 存量复检 / 数据清理 / 统计告警 / 手动触发 | **不可**（会重复执行） |

## 模块结构

源码采用标准 `src` 布局，包目录 `src/freeproxypool/`，包名与发行名一致。

```
src/freeproxypool/
├── __init__.py          # 包元信息，暴露版本
├── __main__.py          # 支持 python -m freeproxypool
├── proxyPool.py         # CLI 入口（click）
├── config_center.py     # 动态配置中心（环境变量 > Redis > 默认值）
├── setting.py           # 默认配置常量
├── log_sink.py          # 日志汇聚常量
├── metrics.py           # Prometheus 指标定义
├── core/                # 核心基础：版本 / 异常 / 日志 / 校验 / 安全 / 脱敏
├── db/                  # 存储层：Redis 客户端 / 队列 / MySQL 冷存储
├── fetcher/             # 采集层：声明式采集源 + 注册表
│   └── sources/         # 各采集源实现
├── gateway/             # API 网关：FastAPI 分发 / 管理后台 / 指标
├── helper/              # 校验与诊断：TCP/HTTP/HTTPS 探测 / 地域 / 声誉
├── services/            # 进程实现：collector / validator / scheduler
├── sdk/                 # 客户端 SDK（同步 / 异步，不依赖项目内其他模块）
├── storage/             # MySQL 冷存储归档
├── util/                # 告警 / HTTP 请求工具
├── admin/               # 管理后台静态资源（templates/admin.html）
├── examples/            # 集成示例（Scrapy 下载中间件）
├── tools/               # 运维工具（CI 门禁 / 每日快照）
└── tests/               # 离线自检套件
```

### 分层原则

- **core**：所有模块都会用到、且不依赖任何业务模块的公共能力（版本、异常、日志、校验、安全、脱敏）。禁止 import 业务模块，避免循环导入。
- **db**：存储抽象。Redis 是权威存储（Hash 存元数据、ZSet 做索引、List 做队列），MySQL 仅作可选冷存储归档。
- **fetcher**：采集层。新增采集源只需在 `fetcher/sources/` 放一个 `.py`，声明式注册，无需改动其他代码。
- **gateway**：唯一的对外入口。FastAPI 应用装配、路由、鉴权、限流、指标。
- **helper**：校验与诊断能力。三层递进校验、地域解析、ASN、DNSBL 声誉、单代理深度诊断。
- **services**：四个进程的具体实现。每个进程一个 `main()` 入口。
- **sdk**：对外客户端。**不依赖项目内任何模块**，外部调用方拷走 `sdk/` 一个目录即可使用。
- **storage**：MySQL 冷存储。归档访问日志、代理历史、系统配置。
- **util**：告警推送、HTTP 请求工具。

## 关键技术选型

| 领域 | 选型 | 理由 |
|------|------|------|
| Web 框架 | FastAPI + Uvicorn | 异步原生支持，与校验层 aiohttp 同构，自动生成交互式文档 |
| 权威存储 | Redis | Hash + ZSet + List 三结构覆盖元数据、索引、队列；O(1) 计数避免全池扫描 |
| 异步校验 | aiohttp + aiohttp-socks | 异步高并发探测；SOCKS 代理需连接器在构造时绑定，故用 aiohttp-socks |
| 采集 HTTP | requests | 同步采集，简单可靠，项目已有依赖 |
| 冷存储 | SQLAlchemy + PyMySQL | 可选归档，默认关闭 |
| 调度 | APScheduler | 存量复检、数据清理、统计告警的定时任务 |
| 监控 | prometheus-client | Prometheus 指标格式 |
| CLI | click | 子命令清晰，支持 `-h/--help` |
| GeoIP | maxminddb | 纯 Python reader，读取 GeoLite2 Country + ASN mmdb |

## 数据流

1. **采集**：`collector` 按 `FETCH_INTERVAL` 周期扫描启用的采集源，解析出代理地址，过滤内网/保留地址，三层去重（本轮内存 → 有效池 → 黑名单），推入待验队列。
2. **验证**：`validator` 消费队列，对每个代理执行三层递进校验：
   - 第一层 TCP 连通探测，不通直接拉黑；
   - 第二层经代理请求目标，记录延迟、出口 IP、匿名度，再探测 CONNECT 隧道能力；
   - 第三层连续 N 轮全通过才判定有效。
3. **分发**：`gateway` 接收客户端请求，按策略（延迟优先/随机/轮询）从有效池取代理返回。
4. **回报**：客户端发现代理失效，调用 `POST /report/`，服务端立即剔除并拉黑。
5. **调度**：`scheduler` 周期执行存量复检、数据清理、统计告警、地域索引重建。

## Redis 数据结构

- **Hash**（`{table}`）：代理元数据（proxy、https、score、region、source、check_count、error_count、ewma_speed 等）
- **ZSet** 索引：评分索引、HTTPS 索引、过期索引、黑名单索引、地域索引（`{table}:region:{CODE}`）
- **List**（`{table}:queue`）：待验队列，带长度上限与背压裁剪
- **配置 Hash**（`fpp:config`）：运行期热更新的配置项
- **统计 Hash**（`fpp:stat`）：采集/校验统计
- **日志 List**（`fpp:logs`）：最近日志（容量上限 2000）

`HLEN` + `ZCARD` 实现 O(1) 池统计，不再每次请求全量扫描。

## 采集源

采集源采用声明式注册：在 `fetcher/sources/` 下放一个 `.py`，定义继承 `BaseFetcher` 的子类并声明 `name`，注册表自动扫描发现。当前内置 38 个采集源（30 个默认启用），单源熔断（连续失败达阈值进入冷却，冷却结束自动复位），指数退避重试。
