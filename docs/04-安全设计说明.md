# 04 - 安全设计说明

## 安全架构

FreeProxyPool 的安全设计以 **fail-closed** 为核心原则：当依赖（Redis）不可用或配置读取失败时，
行为是"拒绝服务"而非"放开大门"。安全相关的配置读取、鉴权、限流在故障时一律收紧，
绝不静默回落到"不鉴权 / 不限制"的默认值。

安全能力分层：

| 层 | 安全能力 | 实现位置 |
|----|----------|----------|
| 配置层 | fail-closed 语义、口令哈希、密钥派生 | `config_center.py`、`core/security.py` |
| 网关层 | API Key 鉴权、限流、CSRF、登录锁定、XFF 可信代理 | `gateway/deps.py`、`gateway/api.py`、`gateway/admin_api.py` |
| 输入校验层 | 代理地址、地域、URL 白名单、SSRF 防护 | `core/validators.py`、`core/iputil.py` |
| 日志层 | 凭据脱敏 | `core/redact.py`、`core/logging.py` |
| 响应层 | 安全响应头、异常不泄露 traceback | `gateway/api.py` |

## fail-closed 配置语义

配置中心 `config_center.py` 把配置读取拆成两种语义：

- **`get(key, default)`**：普通参数，Redis 异常时回落到默认值（保持可用性）。
- **`get_secure(key)`**：安全相关参数，**读不到就报错**（fail-closed），抛 `BackendUnavailable`（503）。

安全相关参数（`API_KEY`、`ADMIN_ENABLED`、登录限流阈值等）一律走 `get_secure`。
这样 Redis 抖动时，行为是"拒绝服务"而不是"鉴权关闭、后台意外开启、限流放开"。

自检套件专门覆盖这一回归：模拟 Redis 故障，断言 `get_secure` 抛 503、鉴权不放开、限流不放开。

## API Key 鉴权

- 开启 `API_KEY` 后，所有分发与运维接口（`/get/` `/batch/` `/pop/` `/all/` `/count/`
  `/delete/` `/report/` `/stats/` `/metrics`）均需携带请求头 `API-KEY: <key>`。
- 鉴权使用**恒定时长比较**（`core/security.py: constant_time_compare`），避免时序侧信道。
- `API_KEY` 留空 = 不鉴权，仅限受控内网自测，生产必须设置。
- 未配置 `API_KEY` 时接口放行（便于本地调试）；一旦配置，无 Key / 错误 Key 一律 401。

## 限流与降级

- 按标识（客户端 IP）QPS 限流，阈值 `RATE_LIMIT_QPS`（默认 50，0 = 不限）。
- **Redis 故障时降级为进程内限流**，而非无限制放开。读不到配置时回落到默认 QPS，
  进程内限流桶仍提供上界，杜绝 fail-open 回归。
- 超限返回 429。

## 管理后台鉴权

管理后台（`/admin` 及 `/admin/api/*`）经过四道关卡，顺序固定：

1. **`ADMIN_ENABLED` 开关**：作用于**整个** `/admin` 前缀（路由级依赖统一校验）。
   旧版只检查 HTML 页面、接口不检查，关掉后台后接口仍可用——现已修复，开关关闭时
   登录接口与所有后台接口均返回 401。
2. **管理会话鉴权**：登录成功后颁发会话令牌（`X-Admin-Token`），校验通过才放行。
3. **CSRF 校验**（写操作）：写操作需携带 `X-CSRF-Token`，由 `core/security.py: derive_csrf`
   从会话令牌与 CSRF 密钥派生，恒定时长比较。
4. **参数校验**：所有输入经 `core/validators.py` 校验。

### 登录锁定

- 连续登录失败达 `LOGIN_MAX_FAIL`（默认 5）次后锁定该来源，锁定时长 `LOGIN_FAIL_TTL`（默认 600 秒）。
- 失败计数按**可信来源 IP**（`gateway/deps.py: client_ip`）统计，锁定提示返回的是锁定时长秒数。
- 锁定 Key 做哈希归一化，超长伪造值不会撑大 Key（防内存打爆）。

### 口令存储

- `ADMIN_PASSWORD` 写入 Redis 前经 PBKDF2-HMAC-SHA256（12 万次迭代 + 16 字节随机盐）哈希，明文不落库。
- 口令强度要求：长度 ≥ 10，且大写/小写/数字/特殊字符至少命中 3 类。弱口令被拒绝。
- 仍使用默认口令时，首次登录强制跳转改密（`ADMIN_FORCE_PASSWORD_CHANGE`）。
- 后台配置接口不回显口令明文，只返回 `has_value`。

## 可信代理与 XFF

- 默认**完全不采信** `X-Forwarded-For`，一律使用 TCP 对端地址。这是对"伪造 XFF 绕过登录限流"的修复。
- 仅当直连来源命中 `TRUSTED_PROXIES`（CIDR 网段）时，才采信 XFF 首项。
- 前置 Nginx 时，`TRUSTED_PROXIES` 填 Nginx 所在网段；不前置代理时留空（最安全）。

## SSRF 防护

服务端会主动发起请求的三个入口均做协议白名单 + 内网主机黑名单双重校验：

1. **采集源 URL 覆盖**（`validate_fetch_urls`）：仅允许 `http`/`https` 协议，拒绝
   `file`/`ftp`/`gopher`/`javascript` 等；拒绝内网/保留地址（`169.254.169.254`、
   `127.0.0.1`、`10.0.0.0/8` 等）；URL 数量超限被拒。
2. **告警 Webhook**（`validate_webhook`）：由服务端主动请求，内网目标即 SSRF，
   拒绝内网地址；协议白名单校验。
3. **校验目标 URL**（`validate_check_url`）：`HTTP_URL` / `HTTPS_URL` 探针目标，
   拒绝内网地址，仅允许公网地址。

内网/保留地址过滤覆盖 `0/8`、`10/8`、`100.64/10`、`127/8`、`169.254/16`、`172.16/12`、
`192.168/16`、`198.18/15`、`224/4`、`240/4`（实现于 `core/iputil.py: is_internal_proxy`）。

## 输入校验

`core/validators.py` 统一校验所有外部输入：

- **代理地址**（`require_proxy`）：拒绝缺端口、端口越界、前导零、非数字等畸形输入，返回 400。
- **地域**（`parse_area`）：非法值一律 400，不静默回落成"不过滤"。
- **匿名度**（`parse_anon`）：非法值 400，不再静默回落成"不过滤"。
- **分页/大小**（`parse_page`/`parse_size`）：页码下限保护，每页上限 500。
- **TTL**（`parse_ttl`）：非法值 400（不再静默回落），上限裁剪。
- **采集源名**（`validate_name`）：白名单校验，拒绝路径穿越、空格。

筛选类参数口径一致：非法值一律 400，不静默回落成"不过滤"。

## 凭据脱敏

`core/redact.py` 对所有日志输出做凭据脱敏：

- 连接串中的密码被遮蔽（`redis://user:secret@host:6379/0` → 密码替换为占位），主机名保留。
- 日志行中的密码被遮蔽，其他内容保留。
- 普通文本不受影响，非字符串输入安全返回。
- 日志汇聚到 Redis 前统一过脱敏过滤器（`core/logging.py: _RedactFilter`），确保明文密码不落库。

## 安全响应头与异常处理

`gateway/api.py` 为所有响应注入安全头：

```
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
X-XSS-Protection: 1; mode=block
Referrer-Policy: no-referrer
```

- 移除 `Server` 头，不暴露服务端信息。
- 全局异常处理：未知路由返回 404 JSON，404 与 500 均不泄露 traceback。
- `/metrics` 默认需 API Key（`METRICS_AUTH`）。

## 路径防护

- 管理后台模板 `admin/templates/admin.html` 通过 `importlib.resources` 定位，
  不依赖文件系统相对路径，避免路径穿越。
- 采集源注册表基于 `pkgutil` 扫描包内 `sources/` 子模块，不拼接用户输入路径。
- `VERSION` 文件、日志目录通过有界向上搜索定位，不受工作目录漂移影响。

## 依赖安全

- `requirements.txt` 全部使用 `>=下限,<上限` 区间约束，上限取"下一个已知破坏性变更之前"的最后版本。
- `starlette` 下限 `1.3.1` 为安全底线，覆盖多个已公开漏洞的修复版本（Host 头校验、
  HTTPEndpoint 处理器选择、StaticFiles 路径解析、请求路径校验、form 大小上限）。
- 依赖漏洞扫描通过 `tools/ci_gate.py` 的 `audit` 层（`pip-audit`）执行。
